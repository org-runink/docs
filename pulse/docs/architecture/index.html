Architecture

Architecture

For administrators and developers: the parts of PULSE and how they fit.

The parts

Part What it does
The app A Flutter app for Android (iOS is planned and not yet built). There is no web app. It talks to the backend over gRPC.
The backend One Go server per deployment, on one port: gRPC for the app and API clients, plus a few plain HTTP routes (health, media, sign-in and OAuth callbacks, the website form and website chat, the podcast feed).
The store Every table, account, session and media file, sealed under PULSE's own key on the platform's object store. There is no database. One writer, so one backend instance per deployment.
The models The platform's own inference: open-weight models on Runink's own servers. PULSE calls no outside AI service. See Sovereign inference.
Speech and lip-sync The platform's shared text-to-speech, speech-to-text and lip-sync services. PULSE embeds no speech engine.
The web reader The platform's shared crawler reads public pages for check-ups, leads and market signals, with one identity and robots.txt obeyed. See Web reading.
Connections The customer's own accounts (Instagram, YouTube, LinkedIn, Google, Microsoft 365, HubSpot, a website repository and others), each with the customer's own grant. Tokens are sealed.
TIDDE Runink's platform runs the deployment: it installs PULSE, keeps the accounts and the subscription, and provides the shared services above.

Every call goes through the same chain

Every gRPC call is checked for authentication and authorization. Every method needs a valid session except sign-in and the model status; the caller's role is checked against each method on every call.

From proposal to action

  1. An agent proposes work (a plan, a post, a reply, a lead) from measured inputs.
  2. The plan gate and the shared safety rules check it before it is kept.
  3. A person approves it (Drafts, approval and publishing).
  4. It goes out only if the administrator armed that channel (Switches).

Where data lives

  • All PULSE data is in its sealed store. Credential and personal fields are sealed a second time, column by column, before they are written.
  • Deleting an account deletes its rows in every table that holds a person's data. See Delete your account.

Configuration, switches and operations are in the Admin guide; the API and extension points in the Developer guide.
