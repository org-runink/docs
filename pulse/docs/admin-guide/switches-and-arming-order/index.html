      Switches and arming order

      Switches and arming order

      Runink PULSE: Prescriptive Unified Lead & Social Engine ships with every outward action switched off. This page lists each switch in one place: what it defaults to, what it does, and the order to turn them on safely. The detail behind each one is on Publishing controls and Users and access.

      Set these on TIDE’s PulseControlPlane resource or its overlay, never on the live Deployment. The operator puts back anything changed on the Deployment.

      Yes and no values

      The keys do not all parse yes and no the same way, and the difference matters:

      • PULSE_APPLY_ENABLED arms only on the exact value true. yes, on, 1, and TRUE leave it off, and the server warns with PUBLISHCFG-AMBIGUOUS.
      • PULSE_PUBLISH_<CHANNEL>, PULSE_AUDIT_APPLY, and PULSE_OUTBOUND_CALLS accept 1, t, true, y, yes, on and 0, f, false, n, no, off, in any case. Anything else, including empty, counts as unset, which for the last two means off.
      • AUTH_GOOGLE_ONLY is on only for the exact value true. PULSE_GRPC_REFLECTION is on for true in any case.
      • SELF_HEAL_AUTONOMOUS and PULSE_WHATSAPP_AUTOREPLY are the two keys whose own default is on, so they read the other way round: they take the same tokens, and unset or unparseable leaves them on. Only an explicit no turns them off.

      The switches

      KeyDefaultEffect
      PULSE_APPLY_ENABLEDoffThe global kill switch for every outward channel, the first half of the audit-apply gate, and what starts the daily site-audit engine. While it is off, nothing publishes and the audit’s Publishing schedule step reports skipped.
      PULSE_PUBLISH_<CHANNEL>follows the kill switchNarrows one channel: BLOG, PODCAST, AUDIOBOOK, YOUTUBE, INSTAGRAM, SPOTIFY, LINKEDIN. Can only turn a channel off.
      PULSE_PUBLISH_CONFIG_PATH, PULSE_PUBLISH_CONFIG_JSON/etc/runink/pulse-publishing.json, noneThe same per-channel opinions as a file, or inline JSON. An environment key wins over the file.
      PULSE_PUBLISHER_USER_IDSempty, which means nobodyUser ids (the users.id column, not emails) allowed to publish through the channels that post as the deployment: LinkedIn, blog, podcast, and audiobook. Anyone else’s dispatch is recorded withheld.
      PULSE_PUBLISH_LINKEDINfollows the kill switchKeep this false to keep LinkedIn drafts-only. See the daily LinkedIn draft.
      PULSE_LINKEDIN_CTA_URLhttps://runink.orgThe address the daily LinkedIn draft ends with.
      PULSE_AUDIT_APPLYoffThe second half of the audit-apply gate. With the kill switch, it allows the Site Audit’s apply, commit, and pr modes, for administrators only.
      PULSE_APPLY_ROOTunset, which refuses every modeThe only directory a Site Audit repo_path may resolve into. Applies to plan too.
      PULSE_OUTBOUND_CALLSoffAllows CallLead to dial through the deployment’s Asterisk trunk. Independent of the kill switch. The caller must also be an editor or admin.
      PULSE_PUBLIC_BASE_URLunsetThe public origin for absolute podcast-feed links. Without it, an armed feed answers 503 instead of rendering links nobody can fetch.
      PULSE_ENVunsetproduction (any case) turns the startup security check from a warning into a refusal to start. TIDE’s k0s overlay sets it. See below.
      PULSE_GRPC_REFLECTIONofftrue turns on gRPC reflection. For local work only; PULSE_ENV does not affect it.
      AUTH_ALLOWED_EMAILSempty, which means nobodyWho may sign in with Google.
      AUTH_GOOGLE_ONLYoffExactly true hides the password form.
      AUTH_SEED_USERSunsetOperator-granted roles as email=persona,…, re-applied at every start. See Seeded roles.
      SELF_HEAL_AUTONOMOUSonAn explicit no stops the self-healing loop applying anything; plans are still reasoned and recorded. See Operations.
      PULSE_WHATSAPP_AUTOREPLYonAn explicit no stops PULSE answering inbound WhatsApp and SMS messages; they are still received. See Telephony and messaging.

      Every switch is also reported at startup. Look for the PUBLISHCFG lines, including PUBLISHCFG audit-apply: armed=…; PULSE_APPLY_ROOT set=…; callers must be admin, and for security config validated.

      Safe arming order

      Turn things on one at a time, and check the startup log after each restart.

      Confirm the production gate passes

      With PULSE_ENV=production, the server refuses to start on an insecure configuration. Before setting it, confirm that the current pod logs security config validated. See Operations.

      Name who may publish as the deployment

      Set PULSE_PUBLISHER_USER_IDS to the owner’s <user-id>, read from the id column of the users table. Do this before arming, so that the moment the kill switch goes on, only the owner’s content can leave on LinkedIn, the blog, or the podcast feed.

      Narrow the channels you do not want

      Set PULSE_PUBLISH_<CHANNEL>=false for each channel that must stay off, including PULSE_PUBLISH_LINKEDIN=false if LinkedIn is to stay drafts-only. Narrowing first means arming the global turns on only what you meant.

      Arm the kill switch

      Set PULSE_APPLY_ENABLED=true. Check one PUBLISHCFG <channel>: armed=… line per channel, and that the audit-apply line still says armed=false.

      Arm server writes, only if you need them

      To let administrators apply Site Audit fixes, set PULSE_APPLY_ROOT to the directory that holds the site checkouts, then PULSE_AUDIT_APPLY=true. Leave both unset to keep the server read-only.

      Arm outbound calls, only if you need them

      Set PULSE_OUTBOUND_CALLS=true once the Asterisk settings are in place and the compliance work for calling real numbers is done. See Telephony and messaging.

      To disarm, reverse the order, or simply unset PULSE_APPLY_ENABLED: that stops every channel, the audit-apply modes and the daily site-audit engine at once. It does not stop outbound calls, WhatsApp and SMS replies, or self-healing, each of which has its own key.

      PULSE_ENV=production

      TIDE’s k0s overlay sets PULSE_ENV=production on the PulseControlPlane, so it takes effect when that resource is applied. With it set, the server refuses to start, logging refusing to start in production, when:

      • the session key (PULSE_JWT_SECRET) is missing or is one the platform refuses, or
      • the app is not served same-origin (PULSE_WEB_DIR is empty) and CORS_ALLOWED_ORIGINS is unset or contains *.

      A missing or refused session key stops startup whatever PULSE_ENV says; what production adds is that the CORS problem stops it too, instead of warning.

      PULSE_ENV also changes one TLS log line. It does nothing else: no billing, metering, or plan behavior reads it, and it does not turn reflection on or off.

      Image build arguments

      The backend image (grpc/Dockerfile) takes its base images through two build arguments, each base pinned by digest. Point them at a registry mirror and the same digests come from there.

      Build argumentDefaultBases
      BASE_REGISTRYdocker.io/librarygolang:1.26-bookworm (build) and debian:bookworm-slim (runtime)
      FLUTTER_SDK_REGISTRYlocalhost:5000/runinkflutter-sdk:3.47.7 (web bundle)

      BASE_REGISTRY defaults to the upstream registry. The Flutter SDK image is built by the platform and served from the cluster’s own registry, so a build elsewhere needs FLUTTER_SDK_REGISTRY pointed at a registry that holds it.
