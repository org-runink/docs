Admin guide

Admin guide

This guide is for the administrator of a PULSE deployment: who may sign in and with which role, the settings, the connections to outside accounts, and the switches that decide what PULSE may publish, send or call. Runink's TIDDE platform installs and runs the deployment; this guide covers what you configure on it.

  • Users and access: Approved accounts only, Google sign-in, roles from the subscription, and where Admin lives.
  • Switches and arming order: Every publishing, sending, calling and sign-in switch with its default, and the safe order to turn them on.
  • Configuration reference: Every environment variable the backend reads, grouped by purpose.
  • Connections and setup: Business profile, and what to configure for Meta, Google, LinkedIn, GitHub, email and voice.
  • Publishing controls: The kill switch and per-channel arming for everything outward-facing.
  • Site pipeline: Blog posts to your site, the daily site audit, and audit-fix pull requests.
  • Telephony and messaging: AI calls to leads and the WhatsApp/SMS edge.
  • Agents that reach the user: Agents ask the owner one short question, in the app and, only if allowed, by SMS or WhatsApp.
  • Answer vendor pitches: How PULSE answers a vendor's pitch with the account's own counter-offer, and every gate on it.
  • First response to enquiries: How PULSE acknowledges a new website enquiry: switches, arming order and every gate.
  • Knowledge probe: An on-demand report of what the model knows in PULSE's own domains: how to run it and what it writes.
  • Web reading: How PULSE reads the public web: one identity, robots.txt obeyed.
  • Billing: The Subscription tab and where its figures come from.
  • Plans and the trial: What an administrator must know: approved accounts, the 14-day trial, roles.
  • Operations: Health, self-healing, TLS, logging, rate limits, and the licence gate.

Access and roles

  • Approved accounts only. People sign in with Google, and only addresses on the deployment's allowed list get in. There is no open sign-up and no self-invite.
  • Roles are viewer, editor and admin. The subscription on Runink's TIDDE platform sets each listed account to editor or viewer, and makes it read-only when a trial ends or a subscription is cancelled. It never makes anyone an admin: administrators are added by Runink.
  • Details: Users and access.

What is on, and what is off

Everything outward is off by default: publishing to every channel, email, SMS and WhatsApp, AI calls, the website chat, lip-synced videos and Autopilot. Each needs its switch, and most also need a person's approval of each action. Work through Switches and arming order before you turn anything on.

The parts you configure

Part What it is
Backend One server per deployment; the Android app talks to it over gRPC.
Data Every table, account, session and media file is sealed in PULSE's own store on the platform's object store. One writer, so one backend instance per deployment.
Models The platform's own inference; no third-party model or API is ever called. See Sovereign inference.
Speech and lip-sync The platform's shared speech and lip-sync services, configured on the TIDDE side. PULSE only points at them.
Secrets OAuth tokens and passwords are sealed with the deployment's envelope key before they are stored.

First things to set

Setting Why
PULSE_JWT_SECRET Required. The server will not start without it.
TIDDE_ENVELOPE_KEK Required. The store refuses to open without it, rather than write tokens in plaintext.
TENANT_ID Names the tenant for billing, the profile page and the Admin page.
CORS_ALLOWED_ORIGINS Required in production: the pinned origins that may call the API (no wildcard), or the backend refuses to boot.
INFERENCE_REMOTE_URL, INFERENCE_MODEL The platform's model router, and the model name requests carry.
AUTH_ALLOWED_EMAILS Who may sign in with Google. Empty means nobody.
PULSE_PUBLIC_BASE_URL The https address of your deployment. Needed by every sign-in connection, Instagram media and the podcast feed. See Public address and redirects.

Then work through Switches and arming order. The full list is in the configuration reference.
