      Leads, opportunities and accounts

      Leads, opportunities and accounts

      The services behind Leads, Opportunities, AI calls, agency clients and Settings › Integrations. Package pulse.v1; the least role of each method is in its table. See Leads and Connections.

      Notes

      • Integrations are the caller’s own rows, so reading them is open to a viewer and changing them needs an editor, not an admin. HubSpot and GitHub connections go through the shared ConnectionsService instead; see Shared components.
      • Sign-in connections. StartSocialConnect returns the consent address for instagram, youtube or linkedin (company_pages adds the LinkedIn page scopes when LINKEDIN_COMPANY_PAGES is on). The platform returns to /oauth/social/callback, which seals the tokens. The answer is configured=false with a message when the server has no app client or no https PULSE_PUBLIC_BASE_URL. ListSocialConnections reports one status per platform and, per feature, the permissions needed and granted. DisconnectSocial revokes the grant at the platform where its API allows, then deletes the sealed tokens. See Setup.
      • Outbound. SendOutreachEmail needs PULSE_PUBLISH_EMAIL armed and a connected mailbox; CallLead needs PULSE_OUTBOUND_CALLS; AICallService.PlaceAICall needs PULSE_AI_CALLS and the lead’s recorded consent. See Switches and arming order.
      • Agencies. A client is its own owner id. Sending x-pulse-client with a client the caller is a member of makes that client the caller.
      • Opportunities are read from open procurement data; nothing is sent or submitted.

      LeadService

      Synced CRM leads — currently HubSpot contacts. ListLeads reads the local cache table; SyncLeads triggers a live pull from the configured CRM integration (see IntegrationService above for how the access token is stored) and upserts into that cache.

// Lead is a synced CRM contact — deliberately a thin, read-mostly local
// cache of what the CRM already tracks, not a PULSE-owned lead-scoring
// model (avoids the two systems disagreeing about what a lead even is).
message Lead {
  string id = 1;
  string platform = 2;          // "hubspot"
  string external_id = 3;       // the CRM's own contact ID
  string email = 4;
  string first_name = 5;
  string last_name = 6;
  string company = 7;
  string lifecycle_stage = 8;   // CRM's own lifecycle stage string, shown as-is
  string lead_status = 9;
  google.protobuf.Timestamp crm_created_at = 10;
  google.protobuf.Timestamp last_synced_at = 11;
  // PULSE acquisition-pipeline stage: "new","contacted","qualified","won","lost".
  string pipeline_stage = 12;
  string phone = 13;
  string title = 14;            // job title / role
  string notes = 15;
  string source = 16;           // "hubspot","manual","webform"
  // The deal's value in minor units of `currency` (cents for EUR). Unset =
  // not valued yet, which is not a value of 0.
  optional int64 deal_value_minor = 17;
  string currency = 18;         // ISO 4217, e.g. "EUR"
  // When the lead last moved to "won"; unset for any other stage.
  google.protobuf.Timestamp won_at = 19;
  // The next follow-up step PULSE suggests for the lead's stage:
  // "first_message" (new), "follow_up" (contacted), "book_call" (qualified),
  // or "" for won/lost. next_step_due is when, counted from the stage change
  // (1, 3 and 2 days); a cadence PULSE sets, not a date anyone agreed.
  string next_step = 20;
  google.protobuf.Timestamp next_step_due = 21;
  // When the newest reply to an email PULSE sent this lead arrived; unset =
  // no reply found (or replies are not tracked for the mailbox).
  google.protobuf.Timestamp replied_at = 22;
  string reply_snippet = 23;    // a short plain snippet of that reply
  // How PULSE would take next_step for the user: "email", "ai_call",
  // "whatsapp" or "sms", chosen from what the lead record holds (an address
  // for email, a number for a call or a message); "" = no way to reach them.
  string next_channel = 24;
  // Where phone came from ("" = not recorded: PULSE never messages it).
  string phone_source = 25;
  // The number replied STOP to PULSE's messaging sender (and not START since):
  // no WhatsApp or SMS is sent to it.
  bool messaging_opted_out = 26;
  // Why the stored address is not usable ("" = it is, or there is none): a
  // placeholder or garbled address kept from before PULSE checked them. Such
  // a lead gets no email task.
  string email_problem = 27;
  // Why next_step_due is not the stage's cadence: "skipped" (put off to
  // tomorrow on To do today) | "churn_risk" (the daily check rated the lead
  // likely to stall and brought the step forward) | "" (the cadence).
  string next_step_reason = 28;
  // The churn check's last verdict: "high" | "medium" | "low"; "" = never
  // checked or no usable verdict (not "low").
  string churn_risk = 29;
  // Its one-line reason, in the model's words; "" when it gave none.
  string churn_reason = 30;
  // When the check last looked at this lead; unset = never.
  google.protobuf.Timestamp churn_checked_at = 31;
}

      OpportunityService

      OpportunityService — Audience › Opportunities (owner, 2026-10-30): public tenders and private requests for proposals that need what the account sells (websites, custom applications, content …), and a drafted response.

      The rules a reader can rely on: * Sources are official open procurement data (EU TED, UK Find a Tender and Contracts Finder, Brazil PNCP, CanadaBuys; US SAM.gov with the account’s own key from Integrations) plus private requests for proposals PULSE’s own crawler finds. No login is scraped. * Each source reports read (with a count), empty, unreadable (with the reason) or not connected. A source that could not be read is never shown as having nothing. * A figure a notice does not state (value, deadline) is absent, never 0. * Matching is the account’s offerings (audit + tuning) mapped to procurement codes (CPV, UNSPSC, NAICS) plus lexical word matching (no embeddings); every card says why it matched. * A drafted response is a draft: nothing here submits anywhere. The person submits, and records it by moving the card to Submitted.

      AICallService

      AICallService places AI voice calls to leads (an AI assistant talks to the lead over Twilio, through org-runink/ui comms/voiceagent) and keeps the records those calls need: the lead’s prior express consent, the lead’s time zone, the tenant’s do-not-call list, each call’s outcome and sealed transcript, and the follow-up task a call leaves behind.

      SERVER-SIDE GUARDS (PlaceAICall refuses, with every reason, unless all hold): - PULSE_APPLY_ENABLED=true, PULSE_OUTBOUND_CALLS and PULSE_AI_CALLS on; - the caller is an editor or admin (read from the users row); - the lead’s phone has a consent record (who recorded it, when and how it was given) for THAT number, not revoked — an AI voice is an artificial voice under the TCPA (FCC, February 2024); - the number is not on the tenant’s do-not-call list; - the lead’s local time (its time zone is required) is inside the calling-hours window, itself inside 08:00–21:00; - fewer than max_attempts AI calls to the lead in the last 30 days, and none in progress; - the tenant’s Twilio caller ID is configured (the call is placed from it). Every call opens with “an AI assistant calling on behalf of” and the company, then the recording notice; “stop” / “do not call” on a call puts the number on the do-not-call list.

      Automations call PlaceAICall as a step with origin “automation:” plus the automation id; a refusal is a result (placed=false, refusals), not an RPC error.
