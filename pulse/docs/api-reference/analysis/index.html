Brand analysis and audits

Brand analysis and audits

The services behind Brand Analysis: the one-line audit and its stages, the diagnosis, material attached to a new-site audit, content research, market research, Google Search Console, and fixes proposed to the customer's own website repository. Package pulse.v1; the least role of each method is in its table. See Audit a domain.

Notes

  • Partial results. A diagnosis can return as a partial result: a part that does not finish is named on the result, and the rest is returned rather than discarded.
  • Judged output. Diagnostic.channel_prescriptions and brand_visibility hold only proposals the plan gate kept; judgements lists every verdict.
  • Audit runs. RunAudit keeps running after the call returns, resumes where it stopped, reuses a recent run unless force is set, and attaches to a run already in flight. Read the report with GetAuditRun (AuditRun.score_report).
  • Progress steps. stage is an informational identifier: show it as-is or map it to your own labels, but do not rely on the set of steps or their order. A step that could not run is skipped, with an error. queue_position is set while a step waits. The terminal event has an empty stage and the run's final run_status.
  • Stored reads. The market research List* methods read what earlier research and audits saved; they search nothing. The service keeps its older proto name.
  • Changing a site. ApplyAuditActions (other than plan) and SiteRepoService.ProposeSiteFix need an admin and the site-change switches your administrator arms; a proposed fix is a pull request on a new branch. See Website repository.
  • Search Console. StartSearchConsoleConnect returns Google's consent address. When the deployment is not set up for it, the answer says what is missing. See Google.

AuditPipelineService

The one-phrase audit ("Audit example.com"): the user types a domain and the PULSE pages are populated from it, ending with research and leads. Each step of a run is tracked, owner scoped, and reported honestly: a step is done only when it produced results or recorded "0 found" from a source that actually answered. A run whose required step failed ends partial or failed, never completed.

AuditAttachmentService

The material a person gives the new-site audit besides text: photos or a short video of the store or product, product documents (PDF, DOCX, TXT, MD) and voice notes. PULSE audits the brand AGAINST that material: does the site say what the documents and photos show, what is inconsistent, which benefits are not communicated.

UPLOAD IS CHUNKED OVER UNARY RPCS (Begin → Chunk… → Finish) because the web client speaks gRPC-Web, which has no client streaming. Every call is owner scoped: an upload or attachment of another user is NOT_FOUND. Bytes are stored encrypted the moment Finish accepts them; nothing is ever written to disk in plaintext. SiteRepoService

The person's own website repository on GitHub (Settings → Integrations → Website repository) and the site fixes PULSE proposes there as pull requests. Proposals go through the GitHub REST API only. PULSE never pushes to the base branch and never merges: a pull request is a proposal. Proposing needs an admin and applying enabled for the deployment.
