Developer guide

Developer guide

Note: What exists today. LUNA has no public API keys, SDK, plugin system or extension points for third parties. Its API is used by the LUNA app itself, and access is for approved accounts only. This guide explains the concepts behind it so that the design is clear; it will grow when outside developers can build on LUNA.

The shape of the system

LUNA is a Go backend that speaks gRPC, and one Flutter app that builds Android and iOS (and a test-only web build). See Architecture.

API concepts

  • gRPC, package luna.v1. Native clients use HTTP/2 gRPC; the test web build uses gRPC-Web. There is no REST API.
  • Sessions. A client signs in with a Google ID token and gets a session token that lasts 12 hours. Every other call carries it as a bearer token. Signing out, or losing approval, ends every session at once.
  • Per account, always. Every read and write is scoped to the session's account. No call can name another person.
  • The plan. WhoAmI tells the app whether the account is on the free tier or the paid plan. A call the plan does not include is refused with a plain reason, and a read-only account can still read everything.
  • Streaming for anything that waits on a model. Such calls stream progress and put the result on the final message. A stream that ends with no result is a failure, never an empty success.
  • Proposals carry a verdict. Anything a model proposed that you might act on comes back with the outcome of its check (agreed, withheld, or "not verified").
  • Metric on the wire. Units are a display choice only. Zero on a body reading means "not reported", never zero.

  • Nothing is written by a model. Writes happen only through explicit calls the person triggered (save a plan, log a set, confirm a pending change).

  • Services: The luna.v1 services and what each one does.

  • Data model: The per-account journal and the records it holds.
