CLI quickstart

CLI quickstart

Your first half hour as a platform developer: build the tidde CLI, bring up the local dev stack, sign in to GitHub, and run a first coding session that changes nothing.

  1. Check the CLI

    tidde --help

    Config resolves from ./tidde.yaml or ~/.tidde.yaml, then TIDDE_* environment variables, then flags (see CLI reference).

  2. Run the apps locally

    tidde dev up runs the apps natively (no VMs, no images, no sudo in the run loop): both app backends, the shared inference server (mistralrs-server), the Flutter UIs, and the security stack.

    tidde dev up            # everything (the default is all)
tidde dev up face       # one app
tidde dev down          # stop everything

    Things tidde dev up needs:

    • The app checkouts. It reads the environment variables FACE_REPO and PULSE_REPO (defaults ../face and ../pulse), not the CLI's --face-repo flag.
    • A mistralrs-server binary and GGUF weights. Without them it logs mistralrs-server binary or model not found under … — apps spawn their own if configured. and carries on.
    • Flutter, for the console UI. Without it you see console skipped (flutter not found).

    Run state goes under .dev/: logs are .dev/*-{backend,frontend}.log, PIDs are .dev/<name>.pid, and ports are written to .dev/ports.env. On first run it mints a dev mesh CA and generates a per-machine encryption key under .dev/secrets/ (delete it to rotate it).

  3. Get portless URLs (one-time sudo)

    tidde dev hosts         # map *.runink.org.local → 127.0.0.1 and grant the gateway :443
tidde dev secure        # optional: add the single mTLS SNI gateway

    The success banner ends with TIDDE dev up (envelope + pipe-mesh + rotating raft mTLS + eBPF + diagnostics/MCP + self-heal). followed by the per-app URLs. The TIDDE console runs as a shell only (/api/* needs the operator and a cluster).

  4. Sign in to GitHub

    tidde auth login        # GitHub Device Flow, cached in ~/.core/auth.json
tidde auth status

    tidde session uses this token by default. Unattended runs can use GitHub App installation tokens instead; the private install guide covers that setup.

  5. Run a first coding session, safely

    tidde session start --repo <owner>/<repo> \
  --prompt "Summarise the README, then call done" \
  --dry-run

    --dry-run runs the full loop but never pushes or opens a PR; it prints the diff instead. With no --inference-url, the CLI probes local endpoints and logs using inference endpoint … (auto-discovered). Every run_shell and browser_* call stops at a [y/N] prompt. See Coding Sessions.

Where the DevEx pages are

In the console, open the DevEx group in the rail. Each page can be deep-linked as ?tab=<name> (for example ?tab=gitops). The DevEx rows are described on the DevEx page, and the whole rail is mapped in the console map.

Deploying to a cluster instead

tidde dev is the local run loop. Deploying to k0s is a different layer: tidde deploy platform|face|pulse|all with --mode local (multipass VMs) or --mode onhost (a single-node k0s on the host itself). See CLI reference.
