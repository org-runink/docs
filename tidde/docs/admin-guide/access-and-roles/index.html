Access and roles

Access and roles

TIDDE admits approved accounts only. Creating an account on the sign-in page does not give access. This page describes who decides access, the roles, the Admin page, the console's write lists, and how TIDDE hands each Runink application the accounts and roles it may serve.

Who may sign in

  • Sign-in is Google only, against a list of approved addresses. An address that is not on the list is refused, and an empty list refuses everyone:. An installation can instead admit every verified address of one approved domain.
  • Admins are added by Runink. Ask Runink to add or remove an admin; it is recorded as a request and applied by TIDDE, which is the single writer of accounts.
  • Members are added by an instance admin, on the Admin page (below).
  • Each installation also has a break-glass administrator sign-in for the installer, described in the private install guide.

Roles

A member of an instance has one role:

Role May
admin everything a writer may, plus manage the instance's members on the Admin page
writer use the instance and change what the console lets a writer change
reader read only

A role can carry an expiry date, after which the grant lapses on its own. During a trial every account has the same 14-day trial; see Trial and subscription.

The Admin page

Admin (?tab=admin) sits at the top of the rail footer. The rail draws it only when the server says you administer the instance in focus (drilled into from the Overview's bird's-eye), and the page refuses to read anything for anyone else. Without an instance in focus it says to choose one first.

Section What it does
Members who may use the instance, and with which role
Carrier: WhatsApp, SMS and calls the contacts an audit may be sent to, and the carrier this instance sends through. Platform console only.
Platform settings the GitHub organisation and the repositories the agents work in, which agent features are switched on, and the cloud providers. Platform console only. Saving is refused unless the console lists you as an admin of that setting.

A member change carries the version of the instance it was made against, so a raced change is refused rather than silently undone. It shows PENDING until the application has picked up the new list. Nobody changes their own access, and the last admin stays.

The console's write lists

Signing in lets you read. A privileged write also needs the console's write list for that kind of change to name you; every attempt, allowed or refused, is recorded in the audit chain. The Harness page (DataEx) shows which lists are set, their size, and whether you are on each.

List Governs When it is not set
Agent admins arming agents, acting on harness findings, changing autonomy, correcting what TIDDE knows, requesting a revert of an improvement, the GitHub configuration every signed-in operator
Connection admins the connection registry and the cloud providers every signed-in operator
Instance admins Ask TIDDE's tools that change something (for example creating a client instance) every signed-in operator
Intelligence admins Intelligence writes, including the actions that dial a data source every signed-in operator
Runner admins adding and revoking data-access runners every signed-in operator; deploying a runner is refused to everyone
Session admins reading the audit trail and ending another person's sessions nobody
FORGE owner FORGE's writes to GitHub nobody

The installer sets the first members of each list (the private install guide names the settings); the session-admin list is then managed on DEVEX › Agent runs.

Warning: If an installation has no sign-in method configured at all, the console reads but refuses every privileged write, because nobody could be named in the audit trail.

Accounts for the Runink applications

TIDDE is the single writer of accounts for the Runink applications (FACE, PULSE and LUNA). For each application it gives the list of accounts the application may serve: the address, its role (writer or reader; nobody is made an application admin this way) and its state. Each application maps the role to its own. A list TIDDE could not provide is named on the Overview's Needs attention. Status: built and in use on Runink's own installation.
