Architecture

Architecture

This page explains how Runink TIDDE is built: what runs on the cluster, and how trust, data and traffic move through it.

What TIDDE is, and what it is not

TIDDE is the shared platform for the Runink applications (Runink FACE: Fulfilment Autonomous Claims Engine, Runink PULSE: Prescriptive Unified Lead & Social Engine and Runink LUNA: Lifestyle Understanding & Navigation Assistant), and FORGE is one of its own console sections. Platform concerns live here: diagnosis and repair proposals, the event mesh, secrets, the object store, inference serving, MCP, PKI and mTLS, telemetry, the Kubernetes operators and the infrastructure as code.

The apps do not import TIDDE. Code that more than one app runs lives in a shared library that TIDDE and the apps both import.

Components

Component Role
tidde the CLI, the single control surface: dev stack, deploys, images, security scans, sessions, the install wizard. See the CLI reference.
TIDDE console the web console, served by the TIDDE operator.
Operators one Kubernetes operator each for FACE, PULSE and TIDDE's generic ClientInstance.
devgateway the edge: a DaemonSet on host ports 80 and 443 that terminates TLS with a leaf from TIDDE's own CA and routes each host to its frontend.
ambassador a small mTLS proxy.
modelrouter the front door to the model plane.
forgecheck the verifier central CI runs on FORGE projects.
tidde-runner the self-hosted data-access runner.

What runs on the cluster

Deployments use k0s with pure kustomize overlays (no Helm). The operators are the authoritative source of each pod's spec and environment.

ClientInstance

ClientInstance (core.runink.org/v1alpha1) is the generic tenant instance the platform places on a shared cluster:

Field Meaning
app the application identity. Drives the core.runink.org/app label and the dedicated-taint toleration.
tenant the tenant key. The core.runink.org/tenant label plus soft node affinity.
role controlplane or runner (default runner): selects the PriorityClass.
image the container image to run.
port the container and service port (default 8080).
replicas default 1; ignored when suspend is true.
tags client labels added to the pod template and ServiceAccount.
placement nodeSelector, tolerations (added to the defaults), affinity (replaces the default soft affinity).
env extra environment variables.
users access grants: email, role (admin, writer or reader, default reader), optional phone, optional expiresAt.
subscription the placement tier and the subscription status (active, suspended or past_due).
suspend scale the instance down.

Every operator gives each pod the same isolation labels and scheduling: core.runink.org/{app,tenant,role}, runink.org/{app,tenant,role}, the toleration core.runink.org/dedicated=<app>, soft (anti-)affinity and a priorityClassName. Each namespace carries a ResourceQuota, LimitRange, PriorityClass, NetworkPolicy and PodDisruptionBudget.

Trust: defence in depth

  • Certificates and mTLS. TIDDE runs its own certificate authority. FACE's application plane is reachable only through mutual TLS. tidde mesh ca creates and distributes the CA.
  • Encryption at rest. The object store and the connection store encrypt what they hold.
  • The object store. TIDDE runs its own S3-compatible object store, with credentials per consumer.
  • App databases. FACE and PULSE encrypt sensitive database values before they are written.

Where the console keeps its data

The console keeps its metadata in its own encrypted store. Each store (agent health, schedules, runs, lineage, governance findings, judgements, session commands and runs, GitHub config, cloud providers, connections, subscriptions) is part of it. The audit chain is tamper-evident, and you can verify it.

The console republishes the few settings the agents read after every change, so change them in the console: an edit made anywhere else is replaced on the next write.

Traffic: the edge and the apps

Each app's web UI is served by its own small frontend. The devgateway edge routes each host to its frontend and handles TLS. When edge sign-in is on, an empty allowlist refuses every sign-in; admitting any verified Google account is an explicit setting.

FORGE runs inside the TIDDE console (FORGE › Studio is a console route), on TIDDE's session.

Inference

The model plane is sovereign: no hosted model is called. Every app and agent calls it by tier, through one front door. Some tiers are served by an inference server outside the cluster and some on the cluster itself; the servers are registered with the console and appear on DEVEX › Clusters. See Models & inference.

Delivery

There is no Argo CD. Delivery is a CI workflow: it builds the images a merge changed, applies the kustomize overlays, rolls the workloads, and records each deploy in the console's lineage record, which DEVEX › Clusters (GitOps) and Agent runs (Deploy lineage) read.

Networking

Manifests work on IPv6 single-stack, IPv4 single-stack and dual-stack clusters: services bind [::], and no Service is pinned to one address family.

Images

tidde build builds local podman images only. The images the cluster runs are built in the cluster (werf and buildah in an ephemeral Job) and pushed to the node-local registry. Every Dockerfile pins its base image by @sha256: digest, and the base images are mirrored with tidde images mirror.

After a delivery roll, workloads run a digest-pinned image, so a bare restart comes back on the same digest. To move a workload onto new images, run the delivery workflow for that image.
