Twins, simulation & claims

Twins, simulation & claims

The action layer.

  • TwinsService is the "actionable twin". It reasons over the fetched estate, proposes action cards (outreach, claims, documents, route changes), and records the human decision on each card.
  • HypothesisService builds the decision options. It proposes scenarios from the estate, simulates them on the sovereign model plane, validates them against the reconciled rules, and promotes them to the twin queue. In the FACE app these are the scenarios on the Options page.
  • ClaimsAgentService triages returned items.
  • FraudLeakageService lists the recovery-leakage and fraud-indicator cards in the order a reviewer works them, and can ask an agent to draft the next step for each.

Nothing on this page executes an action without an explicit approval through ExecuteAction, and an approval is recorded against the verified identity of the session that made it.

Summary

Service RPC Kind Purpose
TwinsService StreamTwins Server streaming Ask the twin agent; stream its reasoning and analysis
TwinsService ExecuteAction Unary Approve or reject an action card
TwinsService GetActionQueue Unary List action cards by status and type
TwinsService OptimizeRoute Unary Compute a route between two places
TwinsService QuickAsk Unary Short retrieval-grounded answer
TwinsService UploadAnalyze Server streaming Analyse an uploaded file with parallel agents
TwinsService GenerateRoadmap Unary Phased maturity roadmap
TwinsService GetSavingsSummary Unary Savings across action cards
TwinsService SubmitFeedback Unary Record feedback on a response
HypothesisService SimulateScenario Server streaming Simulate one scenario, streaming progress
HypothesisService ValidateHypothesis Unary Check a scenario against reconciled rules
HypothesisService GetHypothesisVariables Unary Scenarios proposed from the estate, with their test results
HypothesisService InteractiveSimulate Bidirectional streaming Re-simulate as variables change
HypothesisService SendToTwins Unary Promote a scenario to the twin queue
HypothesisService AnalyzeTelemetry Unary Decompose an equipment telemetry series

FraudLeakageService ReviewClaimsLeakage Unary Recovery-leakage cards by deadline, with an optional agent draft

Several RPCs pass the caller's text through the relevant agent's guardrail rules first. A refusal from the guardrail is returned as an error.

TwinsService

Full name semantics.v1.TwinsService.

StreamTwins

rpc StreamTwins(StreamTwinsRequest) returns (stream StreamTwinsResponse);
  • Kind: Server streaming. Available over native gRPC and gRPC-web.
  • Auth: Bearer session. Tool use inside the agent loop follows the orchestrator's tool gate.
  • Errors: The stream ends with an error (no specific code) if user_query trips the prompt-injection check, or if the agent loop fails before producing an answer.

Runs the twins agent (up to 3 turns) with a context built from:

  • the attached video_frames (the first 3 are shown to the vision model);
  • matching recognised rules;
  • the fetched domain knowledge (always when user_query is set, and narrowed by focus_domains);
  • scenario_context;
  • public research fetched for the query.

audio_input is not transcribed: the model is told that audio was attached and not processed. document_upload and document_filename are not read. Use UploadAnalyze for files.

The stream carries thought messages (progress), then zero or more simulation_result or error messages if the agent triggered a shadow simulation, then one final analysis message. The final message's content is the analysis as JSON, with decisions, tools, metrics, time_series, shadow_search and spoken_response set from it.

If the agent proposes new data connections, the server creates them through ConfigService.CreateConnection and reports each outcome in a thought message.

Request: StreamTwinsRequest

Field Type Description
user_query string The question or instruction.
audio_input bytes WAV/PCM audio. Not transcribed; the agent is told so.
video_frames repeated bytes JPEG/PNG frames for vision. The first 3 are used.
document_upload bytes Not read by this RPC.
document_filename string Not read by this RPC.
ground_with_knowledge bool Inject the latest posture snapshot and recognised rules into the context.
focus_domains repeated string Narrow that knowledge to these domains.
scenario_context string A scenario handed over from HypothesisService.

Response: StreamTwinsResponse

Field Type Description
content string Text of this message. On the final analysis message, the analysis as JSON.
type string thought, simulation_result, error or analysis.
decisions repeated Decision The agent's decisions. Final message only.
tools repeated ToolCall Tools the agent recommended. Final message only.
metrics EvaluationMetrics Quality figures as the agent reported them. See the message for how to read them.
time_series repeated TimeSeriesInsight Time-series insights.
shadow_search repeated ShadowSearchResult Public research findings used.
spoken_response string A short summary suitable for speech.
audio_data bytes Not populated by this RPC.

ExecuteAction

rpc ExecuteAction(ExecuteActionRequest) returns (ExecuteActionResponse);
  • Kind: Unary.
  • Auth: Bearer session. An approval is refused unless the session carries a verified subject, so that every approval names a principal. A rejection is recorded either way.
  • Errors: PERMISSION_DENIED for an approval that cannot be attributed. INVALID_ARGUMENT for a rejection with no reason, or a reason over 2,000 characters (refused, never truncated). FAILED_PRECONDITION if the instance has no action store. NOT_FOUND if action_id does not exist. INTERNAL if the card cannot be read or stored, or if sending the card's email fails.

user_approval must be exactly approve to approve. Any other value is a rejection.

On approval, the server runs the card's artefacts:

  • the email draft is sent through the tenant's connected Google account;
  • calendar invites and ERP updates are reported in not_executed;
  • an attached evidence document is sealed.

On rejection nothing runs, and the evidence document is not sealed. In both cases the decision is appended to the card's decision_trail and the card's status becomes Approved or Rejected. Re-sending the same decision is idempotent: the trail is unchanged and the original entry is returned.

Request: ExecuteActionRequest

Field Type Description
action_id string The card's id.
user_approval string approve approves. Anything else rejects.
sop_draft string Not read by the server.
suggested_providers repeated string Not read by the server.
reason string Why, in the decider's words. Required on a rejection, optional on an approval. Whitespace-only counts as empty. At most 2,000 characters.

Response: ExecuteActionResponse

Field Type Description
success bool true unless this was an approval that executed nothing. A rejection returns true. Not a receipt: read transaction_id.
transaction_id string Set only when success is true.
decision_recorded bool The decision was durably stored. true with success: false means stop: the card is decided, nothing was executable, and there is nothing to retry. Real failures arrive as gRPC errors instead.
not_executed repeated string <artifact>:<reason> for each requested artefact that did not run: email:no_google_connector, calendar:not_implemented, erp:not_implemented, billing:charge_failed. Empty does not mean everything ran.
decision ActionDecision The trail entry recorded, or the existing one on a retry.

GetActionQueue

rpc GetActionQueue(GetActionQueueRequest) returns (GetActionQueueResponse);
  • Kind: Unary.
  • Auth: Bearer session.
  • Errors: UNAVAILABLE if the action store cannot be read. The queue is then unknown, not empty.

With an empty status, returns the undecided cards: stored cards, the cards derived from the latest twin run when none are stored, and evidence-document cards derived from the tenant's records. Cards already decided are left out. With status set to Approved or Rejected, returns only stored cards with that status, including their decision_trail.

Request: GetActionQueueRequest

Field Type Description
workflow_type string Keep cards whose type equals this, case-insensitively. Empty keeps all.
status string Keep cards whose status equals this, case-insensitively. Empty means undecided cards.

Response: GetActionQueueResponse

Field Type Description
actions repeated ActionCard The cards.

UploadAnalyze

rpc UploadAnalyze(UploadAnalyzeRequest) returns (stream UploadAnalyzeResponse);
  • Kind: Server streaming. Available over native gRPC and gRPC-web.
  • Auth: Bearer session, writer, admin or service account.
  • Errors: The stream ends with an error (no specific code) for an invalid file name, a guardrail refusal of the name or content, or the first failing agent.

.csv, .tsv and .txt files are read as text. Any other file is described to the agents by name, size and a base64 sample of its first 4 KB, so the agents do not see its full content. Twelve agents then analyse it in parallel. Each streams a thought when it starts and when it answers. The stream ends with one action_card message holding all the analyses, and the server queues a Procurement card for the upload.

Request: UploadAnalyzeRequest

Field Type Description
file_name string File name. Only the base name is used.
file_content bytes The file.
analysis_type string ROOT_CAUSE, SPEND, INVENTORY_HEALTH or GENERAL. Shown in progress text only.

Response: UploadAnalyzeResponse

Field Type Description
content string Progress text, or on the final message all the analyses as Markdown.
type string thought or action_card.
decisions repeated Decision Final message only: one fixed "Review parallel agent analysis" decision, with no confidence.

Phased maturity plan 

rpc GenerateRoadmap(GenerateRoadmapRequest) returns (GenerateRoadmapResponse);
  • Kind: Unary.
  • Auth: Bearer session, org admin only.
  • Errors: Returned without a specific code if industry trips the guardrail or the model call fails.

The model writes the executive summary. The phases are a fixed four-step template (Digitize, Connect, Analyze, Automate) with no duration each: nothing plans how the timeline divides, so duration_months is 0. Investment and ROI are not estimated. The server also queues the first action card.

Response

Message GenerateRoadmapResponse.

Field Type Description
executive_summary string The model's summary.
phases repeated RoadmapPhase The four phases. estimated_investment_usd and expected_roi_percent are 0: not estimated.

GetSavingsSummary

rpc GetSavingsSummary(GetSavingsSummaryRequest) returns (GetSavingsSummaryResponse);
  • Kind: Unary.
  • Auth: Bearer session.
  • Errors: None.

Sums savings over all action cards, with operator decisions applied. Rejected cards are left out. A card counts when it carries a spend card (identified savings), a route card with a stated saving, or a reverse-logistics or freight-forwarding card (the card's transaction_value). Neither figure is realised savings: the platform does not persist whether an approved action was carried out.

Request: GetSavingsSummaryRequest

Field Type Description
time_range string Not applied by the server.
category_filter string Filters savings_by_category only. ALL or empty keeps all. The totals are not filtered.

Response: GetSavingsSummaryResponse

Field Type Description
total_savings_usd double Pipeline: savings on approved and pending cards.
savings_by_category repeated SavingsCategory By category (Procurement, Route, Reverse Logistics, or the card type), largest first.
savings_trend repeated SavingsTrend A single entry for the current ISO week, holding the total.
approved_savings_usd double Savings on approved cards only. Never more than the total.

FraudLeakageService

Full name semantics.v1.FraudLeakageService. Both RPCs need the writer or admin role: they read the instance's evidence connections and, when asked, spend model time on them.

The cards are evidence documents of kind CLAIMS_LEAKAGE and FRAUD_INDICATOR_REVIEW. They are the same cards GetActionQueue returns, and they are approved or rejected there through ExecuteAction. These RPCs only scope, order and, when asked, draft.

A FRAUD_INDICATOR_REVIEW card is never approved. ExecuteAction takes user_approval: "dismiss" (a reason is required; "reject" is read the same way) or "escalate" (opens an investigation case for the Claims or SIU reviewer; the response's transaction_id is the case reference, case-<decision id>). Both are recorded on the card's decision trail and in the decision log; the card's status becomes Dismissed or Escalated, and GetActionQueue with that status lists them. Neither sends, charges or holds anything. "approve" on such a card is refused with FAILED_PRECONDITION, and "dismiss" or "escalate" on any other card with INVALID_ARGUMENT.

A draft is checked by the server before it is returned. Nothing a draft says files, sends, pays, holds or changes anything.
