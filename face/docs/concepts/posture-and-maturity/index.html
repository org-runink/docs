Posture & maturity

Posture & maturity

On Why you see what your data estate looks like and how ready it is: each business area's health, the domains and how they relate, and the readiness indicators. PostureService serves those figures and grounds the other agents.

RPC What it does
GetHealthScore Serves the latest fetch's posture snapshot. With no snapshot, it runs a posture analysis.
BuildDomainGraph The fast half of a session fetch. It derives data domains and their relationships.
AnalyzeEstateCausal A do-calculus intervention over the connected estate (see below).
ListIncidents Data-maturity assessments (DataMaturityAssessment).
GetContext Semantic context items for an agent type.

What is measured

Each domain gets a DomainHealth. Its figures come from what the profiler read. Each value has its *_measured flag set:

Gauge How it's measured
quality_stability_pct Filled values ÷ sampled values, whatever the share. quality_sampled_values and quality_filled_values give the n.
risk_pii_pct The share of columns whose names match personal-data patterns.
lineage_pct, freshness_pct, policy_pct, cost_efficiency_pct Not measured, with the flag false.

There is no letter grade and no health score. What the profiler observes is reported as facts: a join key or a timestamp column is present or not, values were left empty or not, PII-like columns are present or not. issues lists them, for example "no join key detected (lineage risk)" or "incomplete sample values: 49 of 120 filled".

Readiness findings are those facts. Each gap above is one assessment and one measure to take. Its severity is Not graded: no target is set for it.

A failed scan returns an error. With no connected data source, the answer is FailedPrecondition: "connect a data source first".

The empty_trip category is always empty. Nothing in the platform measures empty-trip or deadhead running, so show it as not measured.

Measure wording records where it came from. OptimizationSOP.provenance (MeasureProvenance) says whether a measure was read from a source, computed from measured data, or written by the posture agent. Only the last may be labelled as AI-generated.

Lineage

A join key present is a schema property, not observed lineage. It reads the same whether a source has been pulled a thousand times or never, because it depends only on whether a join key exists.

Observed lineage is a separate record, written by the backend's lineage recorder:

  • Where records come from. Each extraction and each delivery is recorded, and so is each camera ingest.
  • How they're stored. Records are append-only in the object store.
  • What they contain. Structure only: column names, counts, durations, a literal-free query shape and a fingerprint, and a closed-set error class. Never result values, driver messages or credentials.
  • How to read them. LineageService.GetSourceActivity returns per-connection activity over a window:
    • extractions, deliveries and rows.
    • The outcome mix: ok, empty and failed. empty means the source connected and returned nothing, which is neither a failure nor a delivery.
    • error_classes, destinations, and the last_columns names.
    • durable and durable_reason, which say whether the records survive a restart. Without a durable sink, the process keeps only a small in-memory ring.

Some reads aren't in the log. A camera frame ingest is recorded with a row count of zero, because a camera sends frames, not rows. See Vision & CCTV.

The domain graph

In the FACE app, the estate is mapped by the fetch itself: its business-domains phase derives the domains and their relationships from the connections the fetch reads, and Why shows the result. A newly confirmed connection joins the map at the next fetch. There is no manual control to map it again.

BuildDomainGraph derives domains and their structural edges. Measured CORRELATED_WITH edges come from the fetch pipeline instead. See Fetch pipeline.

When connected sources are read, each edge's relation names the kind of evidence behind it, and a guess is named as a guess.

Value sampling is on by default. metadata_only_connection_ids turns it off per connection. Sampled values never appear in a log line, an error, a lineage record or a model prompt.

FACE still serves include_connected_sources for API clients and for AnalyzeEstateCausal. The FACE app calls GetHealthScore only; BuildDomainGraph, AnalyzeEstateCausal, ListIncidents and GetSourceActivity are API calls.

Estate causal analysis

AnalyzeEstateCausal runs an intervention over columns of the connected estate. A node is <qualified dataset>.<column>, carrying the source's own aggregate over that column.

The caller supplies the coefficients (EstateCausalCoefficient), because nothing in a catalogue or a sample measures how much one column moves another.

How to read the response:

  • Read answered first. When FACE cannot answer, it explains why in refusal.
  • weakest_basis is the weakest basis among the edges the effect travelled along.
  • basis_statement is written to be shown verbatim beside the number.
  • node_refusals, edge_refusals, nodes_added and columns_refused give the denominators. A graph of four columns out of nine hundred measurable ones is not a causal graph of the estate.

Reading the results

  • The facts reflect structure, not how the data is used. A key, a timestamp and no PII-like columns don't mean the data is correct, current or governed.
  • A join key present is not lineage. Use GetSourceActivity for what was actually read and delivered.
  • A declared foreign key is a referential constraint, not a causal claim.
  • An estate causal answer reflects the coefficients you supplied. It rests on those coefficients, over the columns that had measurements.
