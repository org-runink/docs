AI safety

AI safety

FACE's agents read a customer's records and propose actions. The controls on this page sit at the points where untrusted text reaches a model, and where a model's output could turn into an action. None of them makes a language model safe against a determined adversary. Together they make attacks harder and bound what an attack can achieve, and each one says where it stops.

Two kinds of untrusted text

FACE treats text a caller types differently from content the platform fetched, because the two carry different risks.

Caller commands: screened before any model call

FACE screens every prompt in layers before it reaches a model. A prompt that is refused never reaches the model, the caller is told it was refused, and the refusal is audited.

Fetched content: fenced as untrusted data

Connector rows, page text, OCR output and earlier model answers derived from them are wrapped by ai.FenceUntrusted before they reach a prompt:

  • Instruction. The model is told explicitly that the fenced block is untrusted data to analyse, that it carries no authority, and that instructions inside it are part of the data and must never be obeyed.
  • An unguessable delimiter. The fence markers are drawn fresh and at random for each call, so content cannot close its own fence.
  • No bytes changed. The content appears verbatim, so legitimate records are not mangled.

OpenBias guardrails

Each agent service has guardrail rules that ship with the backend. A matching rule refuses the request with PermissionDenied and writes a PROMPT_REJECTED audit record, with the actor ID hashed.

The rules cover security abuse (such as prompt injection and attempts to tamper with the audit trail) and bias and ethics (such as discriminatory decisions).

The agent loop

The agent loop (ExecuteLoop) runs only agents that have guardrails. A request for any other agent is refused with a FailedPrecondition.

The voice line

The phone line is the one prompt path a person can reach without an account. Every caller utterance is screened before any model is called.

A refusal is spoken to the caller as a sentence. It is not an error, because an error on this path would be silence on the line. Refusals are audited.

The carrier's webhooks require a valid request signature, and the media socket requires a short-lived token that FACE minted. See Identity & access.

Review of proposed actions

Every proposed action is independently reviewed before a person decides. The reviewer's verdict is shown on the card.

  • An unsupported action is not offered. It is kept only as a record with accepted=false, and never served as a recommendation.
  • "Not reviewed" is never shown as agreement. An action that was not reviewed is marked as such and is never silently accepted.
  • The verdicts stay in FACE. No verdict is written to another platform's store.

Bounding what agents may do

A mitigation against injection has to be paired with limits on what model output can cause:

  • Agent email is always a draft. An email an agent composes is created as a draft in the operator's mailbox for a person to read and send; no agent sends mail on its own, whatever the agent email allowlist or the decision-authority policy says (see Auditability & lineage). Both are still evaluated, and the draft is audited with the recipient hashed, so the record shows what the policy would have allowed.
  • Proposed actions are bounded. Every action an agent proposes is checked against that agent's allowlist of action kinds and approver roles and its OpenBias rules before it is shown, high-risk action kinds (such as moving money) are refused for every agent, and links to hosts outside the deployment's allowed output hosts are removed from answers. Nothing an agent proposes runs until a named person approves it. The one exception is self-healing of FACE's own runtime (restarting a runner, tripping a circuit breaker, scaling, rolling back), which runs automatically, behind its own fixed list of actions and a kill switch.
  • Tool gating. Agent tools are authorised through the security policy engine, against the verified subject of the request. A service-account token holds the Reader tier and cannot reach write-tier tools.
  • Read-only SQL. Agent-issued and user-issued SQL both go through the same read-only check as every other query. See Network egress controls.

Warning: Scope of these controls

  • Indirect prompt injection is an unsolved problem. Fencing makes injection materially harder. The real limit is what output is allowed to do, which is why the controls above cap agent actions.
  • Guardrails reduce risk; they do not remove it. Tests prove the rules fire. They do not prove the rules catch every harmful request.
  • A review verdict is a second opinion. It is a check, not proof. Keep a human in the loop for consequential actions.
