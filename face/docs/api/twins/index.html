      Twins, simulation & claims

      Twins, simulation & claims

      The action layer.

      • TwinsService is the “actionable twin”. It reasons over the fetched estate, proposes action cards (outreach, claims, documents, route changes), and records the human decision on each card.
      • HypothesisService is the simulation lab. It proposes scenarios from the estate, simulates them on the sovereign model plane, validates them against the reconciled rules, and promotes them to the twin queue.
      • ClaimsAgentService triages returned items.
      • FraudLeakageService lists the recovery-leakage and fraud-indicator cards in the order a reviewer works them, and can ask an agent to draft the next step for each.

      Nothing on this page executes an action without an explicit approval through ExecuteAction, and an approval is recorded against the verified identity of the session that made it.

      Summary

      ServiceRPCKindPurpose
      TwinsServiceStreamTwinsServer streamingAsk the twin agent; stream its reasoning and analysis
      TwinsServiceExecuteActionUnaryApprove or reject an action card
      TwinsServiceGetActionQueueUnaryList action cards by status and type
      TwinsServiceOptimizeRouteUnaryCompute a route between two places
      TwinsServiceQuickAskUnaryShort retrieval-grounded answer
      TwinsServiceUploadAnalyzeServer streamingAnalyse an uploaded file with parallel agents
      TwinsServiceGenerateRoadmapUnaryPhased maturity roadmap
      TwinsServiceGetSavingsSummaryUnarySavings across action cards
      TwinsServiceSubmitFeedbackUnaryRecord feedback on a response
      HypothesisServiceSimulateScenarioServer streamingSimulate one scenario, streaming progress
      HypothesisServiceValidateHypothesisUnaryCheck a scenario against reconciled rules
      HypothesisServiceGetHypothesisVariablesUnaryScenarios proposed from the estate, with swarm results
      HypothesisServiceInteractiveSimulateBidirectional streamingRe-simulate as variables change
      HypothesisServiceSendToTwinsUnaryPromote a scenario to the twin queue
      HypothesisServiceAnalyzeTelemetryUnaryDecompose an equipment telemetry series
      ClaimsAgentServiceProcessReverseLogisticsUnaryNot available: no claim records to ground it
      ClaimsAgentServiceTriageReturnItemUnaryDisposition for a returned item
      FraudLeakageServiceReviewClaimsLeakageUnaryRecovery-leakage cards by deadline, with an optional agent draft
      FraudLeakageServiceReviewFraudIndicatorsUnaryFraud-indicator cards by likelihood band, with an optional agent draft

      Several RPCs pass the caller’s text through the relevant agent’s guardrail rules first. A refusal from the guardrail is returned as an error.

      TwinsService

      Full name semantics.v1.TwinsService.

      StreamTwins 

      rpc StreamTwins(StreamTwinsRequest) returns (stream StreamTwinsResponse);
      • Kind: Server streaming. Available over native gRPC and gRPC-web.
      • Auth: Bearer session. Tool use inside the agent loop follows the orchestrator’s tool gate.
      • Errors: The stream ends with an error (no specific code) if user_query trips the prompt-injection check, or if the agent loop fails before producing an answer.

      Runs the twins agent (up to 3 turns) with a context built from:

      • the attached video_frames (the first 3 are shown to the vision model);
      • matching recognised rules;
      • the fetched domain knowledge (always when user_query is set, and narrowed by focus_domains);
      • scenario_context;
      • public research fetched for the query.

      audio_input is not transcribed: the model is told that audio was attached and not processed. document_upload and document_filename are not read. Use UploadAnalyze for files.

      The stream carries thought messages (progress), then zero or more simulation_result or error messages if the agent triggered a shadow simulation, then one final analysis message. The final message’s content is the analysis as JSON, with decisions, tools, metrics, time_series, shadow_search and spoken_response set from it. Identical requests may be answered from a cache with that single final message.

      If the agent proposes new data connections, the server creates them through ConfigService.CreateConnection and reports each outcome in a thought message.

      Request: StreamTwinsRequest

      FieldTypeDescription
      user_querystringThe question or instruction.
      audio_inputbytesWAV/PCM audio. Not transcribed; the agent is told so.
      video_framesrepeated bytesJPEG/PNG frames for vision. The first 3 are used.
      document_uploadbytesNot read by this RPC.
      document_filenamestringNot read by this RPC.
      ground_with_knowledgeboolInject the latest posture snapshot and recognised rules into the context.
      focus_domainsrepeated stringNarrow that knowledge to these domains.
      scenario_contextstringA hypothesis handed over from the lab.

      Response: StreamTwinsResponse

      FieldTypeDescription
      contentstringText of this message. On the final analysis message, the analysis as JSON.
      typestringthought, simulation_result, error or analysis.
      decisionsrepeated DecisionThe agent’s decisions. Final message only.
      toolsrepeated ToolCallTools the agent recommended. Final message only.
      metricsEvaluationMetricsQuality figures as the agent reported them. See the message for how to read them.
      time_seriesrepeated TimeSeriesInsightTime-series insights.
      shadow_searchrepeated ShadowSearchResultPublic research findings used.
      spoken_responsestringA short summary suitable for speech.
      audio_databytesNot populated by this RPC.

      ExecuteAction 

      rpc ExecuteAction(ExecuteActionRequest) returns (ExecuteActionResponse);
      • Kind: Unary.
      • Auth: Bearer session. An approval is refused unless the session carries a verified subject, so that every approval names a principal. A rejection is recorded either way.
      • Errors: PERMISSION_DENIED for an approval that cannot be attributed. INVALID_ARGUMENT for a rejection with no reason, or a reason over 2,000 characters (refused, never truncated). FAILED_PRECONDITION if the instance has no action store. NOT_FOUND if action_id does not exist. INTERNAL if the card cannot be read or stored, or if sending the card’s email fails.

      user_approval must be exactly approve to approve. Any other value is a rejection.

      On approval, the server runs the card’s artefacts:

      • the email draft is sent through the tenant’s connected Google account;
      • calendar invites and ERP updates are reported in not_executed;
      • no outcome fee is charged: the claims-recovery fee applies only to money confirmed as recovered (see Plans and billing);
      • an attached evidence document is sealed.

      On rejection nothing runs, and the evidence document is not sealed. In both cases the decision is appended to the card’s decision_trail and the card’s status becomes Approved or Rejected. Re-sending the same decision is idempotent: the trail is unchanged and the original entry is returned.

      Request: ExecuteActionRequest

      FieldTypeDescription
      action_idstringThe card’s id.
      user_approvalstringapprove approves. Anything else rejects.
      sop_draftstringNot read by the server.
      suggested_providersrepeated stringNot read by the server.
      reasonstringWhy, in the decider’s words. Required on a rejection, optional on an approval. Whitespace-only counts as empty. At most 2,000 characters.

      Response: ExecuteActionResponse

      FieldTypeDescription
      successbooltrue unless this was an approval that executed nothing. A rejection returns true. Not a receipt: read transaction_id.
      transaction_idstringSet only when success is true.
      decision_recordedboolThe decision was durably stored. true with success: false means stop: the card is decided, nothing was executable, and there is nothing to retry. Real failures arrive as gRPC errors instead.
      not_executedrepeated string<artifact>:<reason> for each requested artefact that did not run: email:no_google_connector, calendar:not_implemented, erp:not_implemented, billing:charge_failed. Empty does not mean everything ran.
      decisionActionDecisionThe trail entry recorded, or the existing one on a retry.

      GetActionQueue 

      rpc GetActionQueue(GetActionQueueRequest) returns (GetActionQueueResponse);
      • Kind: Unary.
      • Auth: Bearer session.
      • Errors: UNAVAILABLE if the action store cannot be read. The queue is then unknown, not empty.

      With an empty status, returns the undecided cards: stored cards, the cards derived from the latest twin run when none are stored, and evidence-document cards derived from the tenant’s records. Cards already decided are left out. With status set to Approved or Rejected, returns only stored cards with that status, including their decision_trail.

      Request: GetActionQueueRequest

      FieldTypeDescription
      workflow_typestringKeep cards whose type equals this, case-insensitively. Empty keeps all.
      statusstringKeep cards whose status equals this, case-insensitively. Empty means undecided cards.

      Response: GetActionQueueResponse

      FieldTypeDescription
      actionsrepeated ActionCardThe cards.

      QuickAsk 

      rpc QuickAsk(QuickAskRequest) returns (QuickAskResponse);
      • Kind: Unary.
      • Auth: Bearer session.
      • Errors: Returned without a specific code if the query trips the twin guardrail or the model call fails.

      Answers in two or three sentences from the knowledge graph and the model. It also queues one S&OP card, “Deep Dive: …”, suggesting a full StreamTwins analysis.

      Request: QuickAskRequest

      FieldTypeDescription
      querystringThe question.
      context_hintstringS&OP, INVENTORY, SPEND or WAREHOUSING. Scopes the retrieval.

      Response: QuickAskResponse

      FieldTypeDescription
      answerstringThe answer.
      confidencedoubleA fixed value (0.75), not a measurement. Do not display it as a confidence.
      sourcesrepeated stringknowledge_graph when retrieval found context. Otherwise empty.
      suggested_actionsrepeated ActionCardThe queued deep-dive card.

      UploadAnalyze 

      rpc UploadAnalyze(UploadAnalyzeRequest) returns (stream UploadAnalyzeResponse);
      • Kind: Server streaming. Available over native gRPC and gRPC-web.
      • Auth: Bearer session.
      • Errors: The stream ends with an error (no specific code) for an invalid file name, a guardrail refusal of the name or content, or the first failing agent.

      .csv, .tsv and .txt files are read as text. Any other file is described to the agents by name, size and a base64 sample of its first 4 KB, so the agents do not see its full content. Twelve agents then analyse it in parallel. Each streams a thought when it starts and when it answers. The stream ends with one action_card message holding all the analyses, and the server queues a Procurement card for the upload.

      Request: UploadAnalyzeRequest

      FieldTypeDescription
      file_namestringFile name. Only the base name is used.
      file_contentbytesThe file.
      analysis_typestringROOT_CAUSE, SPEND, INVENTORY_HEALTH or GENERAL. Shown in progress text only.

      Response: UploadAnalyzeResponse

      FieldTypeDescription
      contentstringProgress text, or on the final message all the analyses as Markdown.
      typestringthought or action_card.
      decisionsrepeated DecisionFinal message only: one fixed “Review parallel agent analysis” decision. Its confidence is a constant, not a measurement.

      Phased maturity plan 

      rpc GenerateRoadmap(GenerateRoadmapRequest) returns (GenerateRoadmapResponse);
      • Kind: Unary.
      • Auth: Bearer session.
      • Errors: Returned without a specific code if industry trips the guardrail or the model call fails.

      The model writes the executive summary. The phases are a fixed four-step template (Digitize, Connect, Analyze, Automate) with the timeline split evenly between them. Investment and ROI are not estimated. The server also queues the first action card.

      Request

      Message GenerateRoadmapRequest.

      FieldTypeDescription
      current_scoresrepeated MaturityDimensionCurrent maturity per dimension.
      target_levelint32Target level, 1 to 5.
      timeline_monthsint32Total months. 0 or negative means 18.
      industrystringIndustry, for context.

      Response

      Message GenerateRoadmapResponse.

      FieldTypeDescription
      executive_summarystringThe model’s summary.
      phasesrepeated RoadmapPhaseThe four phases. estimated_investment_usd and expected_roi_percent are 0: not estimated.
      first_actionsrepeated ActionCardThe queued “Begin Phase 1” card.

      GetSavingsSummary 

      rpc GetSavingsSummary(GetSavingsSummaryRequest) returns (GetSavingsSummaryResponse);
      • Kind: Unary.
      • Auth: Bearer session.
      • Errors: None.

      Sums savings over all action cards, with operator decisions applied. Rejected cards are left out. A card counts when it carries a spend card (identified savings), a route card with a stated saving, or a reverse-logistics or freight-forwarding card (the card’s transaction_value). Neither figure is realised savings: the platform does not persist whether an approved action was carried out.

      Request: GetSavingsSummaryRequest

      FieldTypeDescription
      time_rangestringNot applied by the server.
      category_filterstringFilters savings_by_category only. ALL or empty keeps all. The totals are not filtered.

      Response: GetSavingsSummaryResponse

      FieldTypeDescription
      total_savings_usddoublePipeline: savings on approved and pending cards.
      savings_by_categoryrepeated SavingsCategoryBy category (Procurement, Route, Reverse Logistics, or the card type), largest first.
      savings_trendrepeated SavingsTrendA single entry for the current ISO week, holding the total.
      approved_savings_usddoubleSavings on approved cards only. Never more than the total.

      TwinOntologyService and TwinGraphService

      The twin model, defined in semantics/v1/twin.proto. Concepts, the EPCIS mapping and the honesty rules are described in Twin ontology & graph.

      RPCAccessWhat it does
      TwinOntologyService.GetTwinOntologyany roleClasses, relations, identifier schemes and evidence kinds.
      TwinOntologyService.ValidateTwinIdentifierany roleChecks a GLN, SGLN, SSCC, GIAI, GRAI, LGTIN, GSIN or ISO 6346 code and returns its element string, EPC URI (or why it is absent) and Digital Link.
      TwinGraphService.ListTwinEntitiesany roleEntities by class and search, paged.
      TwinGraphService.GetTwinEntityany roleOne entity with its relations and version history.
      TwinGraphService.TraverseTwinany roleA breadth-first walk of 1 to 3 hops.
      TwinGraphService.ListTwinDevicesany roleThe device registry, with heartbeat health.
      TwinGraphService.ListTwinPlanBindingsany roleThe entities a site plan is bound to: one per confirmed zone, dock or yard slot, plus the plan’s Site and Facility.
      TwinGraphService.UpsertTwinEntityeditor or admin, named personWrites an entity version as OPERATOR_CONFIRMED.
      TwinGraphService.LinkTwinEntitieseditor or admin, named personOpens or ends a relation, checked against domain and range.

      HypothesisService

      Full name semantics.v1.HypothesisService.

      SimulateScenario 

      rpc SimulateScenario(SimulateScenarioRequest) returns (stream SimulateScenarioResponse);
      • Kind: Server streaming. Available over native gRPC and gRPC-web.
      • Auth: Bearer session.
      • Errors: PERMISSION_DENIED if the scenario trips the hypothesis guardrail. Template, model and parse failures end the stream without a specific code.

      Streams progress messages (only scenario_id and impact_summary set) through causal, Bayesian and context enrichment and the model’s reasoning, then one final message with the full result. confidence is the top scenario’s confidence as the model stated it. recommendation is Approve when that exceeds 0.8, Reject / More Evidence when it does not, and Review Needed when the model gave no number.

      Request: SimulateScenarioRequest

      FieldTypeDescription
      scenario_idstringScenario id.
      scenario_namestringScenario name.
      variablesrepeated VariableScenario variables.
      reconciled_rulesrepeated RuleRules the scenario rests on.

      Response: SimulateScenarioResponse

      FieldTypeDescription
      scenario_idstringScenario id.
      impact_summarystringProgress text, or on the final message the simulated impacts and hypothesis.
      confidencedoubleThe model’s stated confidence in the top scenario. 0 when none was stated.
      recommendationstringApprove, Reject / More Evidence or Review Needed. Empty when there were no scenarios.
      scenariosrepeated DecisionScenarioDecision scenarios.
      impactsrepeated ImpactSimulationSimulated impacts.
      tracesrepeated EvidenceTraceEvidence traces.
      metricsEvaluationMetricsQuality figures as the model reported them.
      forecastsrepeated TimeSeriesForecastForecasts.
      anomaliesrepeated TimeSeriesAnomalyAnomalies, including decomposition anomalies over the forecasts.

      ValidateHypothesis 

      rpc ValidateHypothesis(ValidateHypothesisRequest) returns (ValidateHypothesisResponse);
      • Kind: Unary.
      • Auth: Bearer session.
      • Errors: None.

      A deterministic check. No model is involved. valid_data is true when a fetch has produced rules or a posture snapshot. Each reconciled rule in Drift, Shadow, Missing or Conflict (stated in the request, or recognised by name) raises a risk flag. valid_logic needs valid data, no risk flags, and at least one rule.

      Request: ValidateHypothesisRequest

      FieldTypeDescription
      hypothesis_idstringHypothesis id. Not used by the check.
      scenario_namestringScenario name, used in the rationale.
      reconciled_rulesrepeated RuleRules the scenario rests on.

      FraudLeakageService

      Full name semantics.v1.FraudLeakageService. Both RPCs need the writer or admin role: they read the instance’s evidence connections and, when asked, spend model time on them.

      The cards are evidence documents of kind CLAIMS_LEAKAGE and FRAUD_INDICATOR_REVIEW. They are the same cards GetActionQueue returns, and they are approved or rejected there through ExecuteAction. These RPCs only scope, order and, when asked, draft.

      A FRAUD_INDICATOR_REVIEW card is never approved. ExecuteAction takes user_approval: "dismiss" (a reason is required; "reject" is read the same way) or "escalate" (opens an investigation case for the Claims or SIU reviewer; the response’s transaction_id is the case reference, case-<decision id>). Both are recorded on the card’s decision trail and in the decision log; the card’s status becomes Dismissed or Escalated, and GetActionQueue with that status lists them. Neither sends, charges or holds anything. "approve" on such a card is refused with FAILED_PRECONDITION, and "dismiss" or "escalate" on any other card with INVALID_ARGUMENT.

      A draft is checked by the server before it is returned. Each step must name a card that was handed in, use an action from the agent’s allowlist and name an approver, and it must pass the agent’s guardrail rules as output. Amounts, likelihood bands and handoff cards on a step are copied from the card, never taken from the model. Nothing a draft says files, sends, pays, holds or changes anything.
