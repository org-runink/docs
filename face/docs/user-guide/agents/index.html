Model cards

Agent model cards

A model card describes one of FACE's agents in plain language: what it is for, what it reads, what it hands a person, who has to approve it, which model it runs on, and where it stops. There is one card for each kind of work you meet in FACE. What an agent finds shows on Ask, its options on Options, and what it drafts for approval on Actionable Twins. Several cards cover more than one agent, because those agents do one job together.

These cards are written for buyers, evaluators and operators. The mechanics behind them are on the Analysis & evidence pages, which these cards link to rather than repeat.

One rule for every card

FACE drafts. A person decides. Every claim, short-pay, filing, order, quarantine, remediation and repair that an agent proposes is a recommendation for a named approver. Nothing is sent, filed, paid or settled until someone with the authority approves it, and the server records who did. The one exception is FACE's own operational self-healing: restarting, isolating, rolling back or scaling FACE itself runs automatically from a fixed list, and an operator can switch it off. The approval tiers and the decision log are described in Auditability & lineage and Agents & oversight.

How to read a card

Every card has the same sections:

  1. What it does: one sentence, then the jobs it handles.
  2. What it reads: the records, documents and systems it takes in.
  3. What it produces: what you get back, and in what form.
  4. Human oversight: what a person approves, and what the agent can never do by itself.
  5. Model: the base model it runs on.
  6. Where it runs and data handling: where inference happens.
  7. Guardrails: the policies it follows, in plain words.
  8. How to read its results: what a result shows, what stays with a person, and when it declines or says data is missing.

To see what each agent produces on real data, load the quickstart estate and ask about it on Ask.

Facts shared by every card

Models. FACE sends each model call to one of three tiers on the deployment's model plane, chosen by the kind of task (see Sovereign models):

  • General reasoning: most agents.
  • Code: rule checks written as code.
  • Vision: documents and images; it starts on demand.

Each tier serves the deployment's own models.

Many of the figures on these cards cite the records they came from. See Evidence documents.

Where inference runs. Every agent calls the model plane of its own FACE deployment: Runink's shared machines on a Trial, the customer's own cloud on Cloud and their own servers on On-premises. FACE calls no outside AI service on any plan. Records an agent reads are passed to the model as fenced, untrusted data, never as instructions (see AI safety). The connections you configure still reach their own systems, and an approved action, such as an email sent through a connected account, goes where that action says.

Guardrails. Each agent's requests are checked against its guardrail rules before a prompt reaches the model, and Every proposed action is independently reviewed before a person decides. Both are described in Agents & oversight and AI safety, including the scope of each.
