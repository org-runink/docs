      Agent Fleet

      Agent Fleet

      Runink TIDE runs its own agents on its own model. The console roster (GET /api/agents) lists eighteen: compliance, curator, datagov, deployer, eval, fixer, hunter, judge, opsdoctor, recon, reviewer, risk, selfheal, triage, resolver, forger, users and session. Each agent is built from source per run, with no third-party SDK.

      The roster

      Roster nameDeliveryTriggerWhat it produces
      reviewerworkflowa pull request opened or updated; a PR comment containing @core_review, @core_check, @code_review or @review; the org-wide review sweepa ✔️ ack comment and core-review label, then PR review comments; findings set review:findings-open
      fixerworkflow (and inline in the review)runs inline on every finding; a @core_fix PR comment; a manual run for one PRa draft correction PR onto the reviewed branch. Never merges
      resolverworkflowa resolve request from the review; every three hours; a manual runa core session on the PR head, then a draft PR onto it
      triageworkflowan issue opened; a manual runa triage comment plus labels
      self-healworkflowa failed run of a build, deploy or apply workflow; a manual run for one runone root-cause comment on the PR. Never pushes code
      riskworkflowdaily at 05:23 UTC; a manual run; a playbook stepthe living “🛡️ Dependency risk report” issue from core scan --json
      complianceworkflowdaily at 01:13 UTC; a manual run; a playbook stepthe living “📋 Compliance status” issue, a control-evidence artifact, and a customer-safe block for release notes
      curatorworkflowdaily at 06:17 UTC; a core @curate / @curate comment; a manual run; a playbook steprelease notes, doc fixes, audits and test scenarios as a curator/<sha>-<runid> PR
      deployerworkflowan @core_deploy issue comment; a manual run for one issuerelease notes: a pull request adding a dated section to the release notes (never merged by the agent), linked on the issue
      datagovworkflowdaily at 07:11 UTC; @core_datagov; a manual run; a playbook stepthe living “🗃️ Data governance status” issue and the console’s findings store. No model
      judgeworkflowdaily at 08:29 UTC; @core_judgement; a manual run; a playbook stepthe living “⚖️ Judgement status” issue and the console’s judgements
      reconworkflowdaily at 09:37 UTC; @core_recon; a manual run; a playbook stepa reconciliation report in the console, and the “🧭 Rules reconciliation status” issue
      opsdoctorKubernetes CronJobevery 30 minutescomments on one tracking issue; makes only small, bounded repairs to the build plane
      evalCLI, plus the inference bench workflowmanual: score, replay, regress, model, bencha trajectory + outcome report and a gate exit code; bench prints TTFT and decode tok/s
      usersworkflowan issue labelled add-users (the tide @add_users form), opened by an org memberpatches spec.users on a ClientInstance, or rebuilds the shared apps’ allowlist
      forgerworkflowfour times a day (03:41, 09:41, 15:41 and 21:41 UTC); a manual runa core session against the oldest open forge brief, as a draft PR. Disarmed by default
      sessionCLIcore session startsee Coding Sessions

      The roster also carries a family (delivery or governance) and a delivery kind (workflow, cli, cronjob). The governance screens take their population from the family. risk, compliance, datagov, judge and recon are governance.

      Models and budgets

      Agents use the general model unless told otherwise; the reviewer and fixer use the coder model. Every model-calling agent goes through the model router, the one front door to the engines. The exceptions are deliberate: the ops doctor must not depend on the hop it reports on, and the inference bench measures the engine itself.

      Agent cost is decode-seconds, not runner-minutes. The model plane serves one request at a time. Every budget derives from one configured rate, INFERENCE_DECODE_TOK_S. It defaults to 3.4 tok/s and is set as an Actions variable of the same name. Each agent derives its token budget from its deadline rather than declaring it separately. At that rate a 2,000-token answer is about ten minutes of pure decode.

      Size budgets from the deployment target, not the dev workstation. The 3.4 tok/s default is an estimate for CPU-only server hardware; measure yours with the inference bench.

      Switches

      Variable (Actions variable of the same name)DefaultEffect
      CORE_FIXER_JUDGEMENT, CORE_SELFHEAL_JUDGEMENT, CORE_TRIAGE_JUDGEMENTonthe shared plan gate judges the agent’s own proposal before it acts. Only off, false, 0, no or disabled turns one off
      CORE_FAST_JUDGEMENTonthe judgement fast path runs in front of the LLM for judge and the three plan gates
      CURATOR_CRON_DRY_RUNunset means drythe scheduled curator publishes only when this is the literal string false
      CORE_FORGE_ENABLEDoffarms the forger

      With the plan gate, a dissent blocks the action. The fixer pushes nothing and reports unresolved, self-heal posts a “withheld” notice, and triage posts the classification with labels withheld. Unable-to-judge does not block: the fixer’s draft is titled [not verified by the judge], and self-heal and triage say NOT VERIFIED. Every run prints a line beginning PLAN-GATE: (off, empty, concur, dissent or unable) with the tally.

      A green curator run proves nothing. A dry run does everything except publish and then finishes green, and an unset CURATOR_CRON_DRY_RUN means dry.

      Started by Atlas playbooks

      Six agents can be started by a playbook step: datagov, compliance, risk, judge, recon and curator. Each runs only when the step names it, and reports its outcome back to the playbook run. A curator started by a playbook is treated exactly like the scheduled run. See Playbooks.

      Pairs that look like duplicates and are not

      PairThe boundary
      curator security audit vs riskThe curator reads first-party code committed since its last run (CWE/OWASP, model-judged). risk runs govulncheck over dependencies (known CVEs, reachable).
      curator compliance audit vs complianceThe curator starts from a diff and asks which controls it touches. compliance starts from the control index, checks every citation still exists, and deep-reads three controls.
      selfheal vs opsdoctorselfheal needs a job that ran and failed. opsdoctor sees jobs that never run and runner pods that crash, from a CronJob outside Actions.
      selfheal vs the apps’ self-healingThe agent diagnoses failing CI runs. The apps’ self-healing restarts, isolates or rolls back an app.
      judge vs eval’s judgeeval scores our agents’ run traces against a golden set. judge assesses someone else’s finding against its evidence.

      Behaviours worth knowing

      • opsdoctor must never become a workflow. It heals the CI plane, so it cannot depend on it. It is the only agent that ships as an image.
      • compliance proposes and cannot apply. Its workflow holds contents: read.
      • datagov holds no credential and dials nothing. It assesses data quality and PII exposure only from what Resolve’s Explore recorded, read from the console. A source nobody explored stays unassessable. See Data governance.
      • judge abstains rather than agreeing. Its outcomes are concur, dissent and unable-to-judge. Submissions are accepted once CORE_JUDGEMENT_INGEST_TOKEN is set. See Judgements.
      • recon calls an ungoverned rule Shadow, so a fresh workspace is mostly Shadow. That is by design.
      • A model failure is loud. reviewer, triage and selfheal post a degraded notice when the model is unreachable instead of exiting green.

      Managing schedules from the console

      GET /api/agent-schedules lists fleet cadence and enablement, and which of it is editable. PUT /api/agent-schedules/{name} arms or disarms an agent with a body carrying at least one of enabled, dryRun or schedule. It is a privileged write gated by CONSOLE_AGENT_ADMINS and audited. In the console this is Agent runs › Runs, “Schedules & arming” tab (?tab=agentSchedules).
