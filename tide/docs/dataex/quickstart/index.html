      Quick start

      Quick start

      From an empty console to a first data audit, using a fictional company you can download. No vendor account, no customer data, nothing to invent.

      This page follows the console’s own Start here panel on the Overview. Those five steps are read from the platform — connect a source, test it, map the estate, run an audit, invite a member — and are never ticked by hand. When this page says a step is done, the console will say so too, because both are reading the same thing.

      Apply the sample systems only to a test instance, never to a production deployment. They are stand-ins with weak, published credentials: a Kafka with no authentication, a PostgreSQL whose password is in the manifest, a Guidewire stand-in with a published login, an RTSP camera with no credentials at all. Use a scratch machine or a scratch cluster.

      What you are about to connect

      One fictional logistics company — Quillmere Freight Lines (quillmere.invalid) — written out in the native shape of every connection type the catalogue offers. The same shipment, order, carrier, claim, SKU and device identifiers appear across all of them, so cross-source reconciliation actually lines up instead of being asserted.

      It carries six planted anomalies. They are the point of the bundle, not decoration — each one is a thing TIDE and FACE should find, and each spans more than one source. In broad strokes they cover:

      • freight billed above its contracted rate;
      • a claim at risk of missing its filing window;
      • a cold-chain temperature excursion;
      • one customer order fulfilled twice;
      • a vehicle off its planned route;
      • goods received that no shipping notice accounts for.

      This page does not spell out the exact values or how each is detected. The bundle’s expected model says what a correct reading finds, so you can check the console’s result against it.

      Step 1 — Connect a data source

      Download the bundle for the source you want and create the connection from DataEx › Connections › New connection.

      # one connection type
curl -LO https://docs.runink.org/downloads/connections/postgres.zip

# or the whole set, with checksums
curl -LO https://docs.runink.org/downloads/connections/SHA256SUMS
curl -LO https://docs.runink.org/downloads/connections/manifest.json

      Each zip holds that platform’s schema in its own idiom, the synthetic rows, and the model TIDE should discover from it. That last part is what makes this testable rather than a showcase: you can compare what the console mapped against what the bundle says it should have mapped.

      Twenty-five types ship as zips. The other seven — cctv, gps, iot, kafka, mqtt, rfid, sensorgateway — are streaming connectors, so a zip is the wrong shape for them. They ship as replays instead:

      curl -L https://docs.runink.org/downloads/connections/streams/mqtt/manifest.json

      A full inventory of both, with a sha256 per file, is in manifest.json, and universe.json describes the whole company. The download folder has no directory listing, so start from the manifest.

      Credentials are write-only. The console never returns one after it is stored; rotating is a separate action. Every placeholder in these bundles is change-me — the publisher refuses to ship anything else, along with any non-documentation IP, any host outside .invalid, and anything over 25 MiB.

      Step 2 — Test the connection

      Test on the connection row. It is not a ping: it is Resolve’s Test run on the connection’s bound runner, so it answers “can the thing that will actually read this reach it?” rather than “is the hostname spelled right”.

      A fresh console has only the built-in Runink managed runner (console). That is enough for every bundle here. Self-hosted runners are for sources TIDE must reach inside your network — see Data-access runners.

      Until a source answers a test, the Overview says so in as many words: “None of your N sources has answered a test yet.”

      Step 3 — Map the estate

      Mapping walks each connected source and records what is in it — datasets, fields, and the domains it infers from them. The Overview then reads “N datasets mapped from M sources”, counted from the platform rather than from this page.

      This is the step where the shared identifiers start paying: the same SHP-50004 in a TMS, a WMS, a telematics feed and a claim file is what lets the next step reconcile across them instead of auditing each in isolation.

      Step 4 — Run the first data audit

      The audit is what the six anomalies are for. A run that finds none of them has not failed politely — it has not read the data, and that is worth chasing rather than accepting.

      Until one has run, the Overview is explicit: “No data audit has run yet.”

      Step 5 — Invite a member

      The last step exists because an audit nobody can open is an audit nobody acts on. Admin is in the rail footer, under the instance row, and appears only for an admin of the chosen instance.

      What stands up locally

      A synthetic fixture is data, not a running system. The FACE quickstart grades say, for every type, whether it stands up locally or needs a vendor account.

      Where the bundles come from

      The bundles are generated from one deterministic source, and every download is checked against a fresh generation before it is published, so the files you download and the expected models agree.
