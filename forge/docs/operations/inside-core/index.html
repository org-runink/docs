      Inside Runink TIDE

      FORGE is a TIDE component. It has no domain, no DNS record, no OAuth client, no login screen, no session store and no sign-out. There is no forge.runink.org. It appears as the FORGE category in TIDE’s console rail, and it never needs a route, origin or record of its own.

      Access and billing

      • FORGE comes with a TIDE subscription and is in preview. It has no price, plan, sign-up or invoice of its own. Whoever can sign in to an installation’s TIDE console, and passes the optional FORGE_OWNER_EMAIL allowlist, can open FORGE there.
      • Model use is TIDE usage. Every planner and judge call records the model slot time against the installation’s TIDE account (CORE_BILLING_ACCOUNT). On TIDE Lite it is metered in CU, where 1 CU is one second of a model slot. On TIDE Dedicated and TIDE Enterprise it is unmetered. Typed commands never call a model and record nothing. See Environment: Metering.

      The path

      1. The browser is at https://core.runink.org/forge/….
      2. TIDE’s console strips /forge and reverse-proxies the request to the FORGE service. That service serves the Flutter bundle and gRPC-web at /.
      3. The bundle is built with --base-href /forge/. The studio therefore resolves its gRPC-web calls relative to the page, as <origin>/forge/<service>/<method>.

      Because of the base href, opening the backend’s own / directly cannot load the bundle’s assets. Locally, use forge dev proxy.

      Identity

      On every request, TIDE’s proxy removes any inbound X-Core-Identity and attaches a fresh assertion, made with github.com/org-runink/security/coreidentity. The assertion is an HMAC-SHA256 over {sub: email, aud: "forge", iat} with a maximum age of two minutes, keyed with CORE_FORGE_IDENTITY_KEY. The key is shared only between TIDE’s console and FORGE.

      Every RPC except gRPC reflection passes through FORGE’s auth interceptors, which verify the assertion. gRPC-web headers reach the interceptor as metadata. A stream is checked when it opens, so the two-minute limit does not cut a stream that started with a fresh assertion.

      CaseAnswer
      Valid assertion, FORGE_OWNER_EMAIL unsetAdmitted. TIDE’s sign-in is the only gate.
      Valid assertion, address listed in FORGE_OWNER_EMAILAdmitted
      Valid assertion, FORGE_OWNER_EMAIL set but the address not in itPermissionDenied: this account is not on this forge instance's allowlist (FORGE_OWNER_EMAIL)
      Missing, malformed, expired, future-dated, wrong-audience, badly signed or duplicated assertionUnauthenticated: FORGE is opened from CORE — sign in to CORE
      CORE_FORGE_IDENTITY_KEY unset, not base64, or shorter than 32 bytesFailedPrecondition naming the variable, on every RPC (fail closed)

      Two assertions on one request mean a proxy failed to strip the inbound one. FORGE refuses rather than guess which one TIDE wrote. A refusal is logged as the coreidentity error sentinel only: the header value is a bearer credential and never reaches a log or a reply.

      The verified email is the actor. IdentityService.WhoAmI returns it, the chat store is keyed by it, and the audit records it.

      What the person sees

      When WhoAmI fails, the studio shows one plain line and an Open CORE button:

      • FORGE is opened from CORE — sign in to CORE.
      • Your CORE account is not on this FORGE's allowlist.
      • FORGE could not check who you are: …

      Any later call that answers Unauthenticated reads as CORE did not vouch for you — sign in to CORE again., because it means TIDE’s session ended. Signing out is done from TIDE’s rail footer.

      How TIDE shows FORGE

      • The rail is FORGE’s chat history: New chat (/forge/?chat=new), then the recent chats, newest first. TIDE reads the list through the same-origin /forge/ proxy, using runink.ui.chat.v1.ChatService/ListChats on the TIDE session.
      • The page header names the chat. The studio reports what it shows with a same-origin postMessage of {"type":"forge.chat","id","title","project"}, which carries ids and display text only. TIDE accepts it only from its own origin and from the studio iframe’s own window.
      • TIDE files no briefs. Filing is FORGE’s alone, through ApproveChat. TIDE’s coding agents consume the forge-labelled issues, and FORGE is their only producer.

      Network

      FORGE’s on-host manifest (merged in core) creates the forge-system namespace, a Service, and NetworkPolicies that admit only TIDE’s console. The image listens on :: because the platform’s pod network is IPv6 single-stack.
